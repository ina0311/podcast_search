pyてよn日記「Git でコミットする時のルール」を指針に、差分や変更概要から最適な Git コミットメッセージを 1 本生成する。

## 実行手順

1. **変更ファイルの確認**
   - `git status` を実行して変更されたファイルの一覧を取得する
   - `git diff` を実行して変更内容の差分を確認する
   - 変更ファイルの一覧を以下の形式で表示する：
     ```
     ## 変更ファイル一覧
     - [変更種別] ファイルパス
       - 変更内容の簡潔な説明
     ```
     変更種別は `M`（変更）、`A`（追加）、`D`（削除）、`R`（リネーム）など。

2. **コミットメッセージの生成**
   - 差分と変更概要を分析し、以下のガイドラインに従ってコミットメッセージを生成する

3. **結果の表示**
   - 生成したコミットメッセージを明確に表示する
   - 必要に応じて、複数の論理的な変更に分割することを提案する

## ガイドライン

1. **言語ポリシー**  
   すべて日本語で記述。共有リポジトリでもチーム合意がある前提で日本語を採用する。

2. **フォーマット**  
   1 行目に `<prefix>: <imperative summary>`（50 文字程度、動詞で開始）。2 行目は空行。3 行目以降で *what* と *why* をそれぞれ箇条書きまたは短い段落で説明する。理由が自明であれば 1 行で完結してよい。

3. **Prefix の分類（例）**  
   - **ファイル/ライブラリ操作**: `add`（新規追加）、`remove`（削除）、`upgrade`（依存更新）  
   - **ユーザ向け機能**: `feat`（新機能）、`fix`（不具合修正）、`change`（仕様調整）、`refactor`（挙動を変えない内部改善）  
   - **設定・インフラ**: `config`（設定やインフラ調整）  
   - **非機能**: `style`（整形や命名調整）、`perf`（性能改善）  
   プロジェクトに既存の prefix があればそれを優先し、上記は迷ったときの参照例とする。

4. **粒度と差分管理**  
   1 コミット = 1 論理変更。関係のない修正は分割し、 diff が大きくなり過ぎる場合は段階的にまとめる。迷ったら「一週間後の自分」に伝わるかを基準に what/why を見直す。

5. **Work in Progress ルール**  
   WIP は Pull Request の進行共有など必要なときのみ使い、通常の履歴には残さない。恒久的な履歴には完成した単位だけを積む。

6. **不足情報への対応**  
   差分や理由が曖昧な場合は即座に追加情報を尋ね、推測で埋めない。

出力は日本語のみで統一し、次のテンプレートに従う。

```
## 変更ファイル一覧
- [変更種別] ファイルパス
  - 変更内容の簡潔な説明
- [変更種別] ファイルパス
  - 変更内容の簡潔な説明

## コミットメッセージ

<prefix>: <imperative summary>

- what: <変更内容を日本語で 1-2 文>
- why: <理由や背景を日本語で 1-2 文>
```

必要なら追加の箇条書き (`how`, `impact`, `notes` など) を添えてもよいが、冗長にならないようにする。

複数の論理的な変更が混在している場合は、分割を提案し、各変更ごとにコミットメッセージを生成する。

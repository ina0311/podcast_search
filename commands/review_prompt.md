# コードレビュー用プロンプト

目的: 差分に対し、品質・安全性・一貫性の観点から短時間で高精度なレビューを行う。

入力（できるだけ埋める）:

- 変更概要: 何を、なぜ、どう変えたか
- リスク: 互換性・パフォーマンス・セキュリティ・運用
- 対象範囲: 影響のある機能/ファイル/API
- テスト: 追加/更新の有無、手動確認手順
- 観点リクエスト: 重点チェック（例: 型安全・エラーハンドリング・境界値）

出力の期待（レビュア指示）:

- まず高リスク事項を上位に簡潔に列挙（最大5点）。
- その後、領域ごとに具体的な指摘と改善提案をセットで記載。
- 必要な場合のみ、サンプルコード/疑似コードを最小限掲載。
- 変更不要な箇所は言及しない（ノイズ削減）。

観点チェックリスト:

- 設計: 責務分離・凝集度・命名・再利用性
- 型安全: any回避、境界のスキーマ化（Zodなど）
- エラー処理: 例外/戻り値、ログポリシー、ユーザへの伝達
- セキュリティ: 入力検証、シークレット、ヘッダ、CORS
- パフォーマンス: N+1、不要レンダ、I/O/CPU重い処理の同期化
- 可観測性: ログ構造化、相関ID、メトリクス下地
- テスト: 単体/結合、クリティカル経路の網羅
- DX/運用: スクリプト、README、エラーメッセージの明確さ

テンプレ（このまま使える）:

```text
目的: <このレビューの目的>
前提: <重要な背景や制約>

最重要指摘（最大5件）:
1. <指摘> — <改善提案>
2. <指摘> — <改善提案>

詳細レビュー:
- <領域/ファイル>: <指摘> — <提案/例>
- <領域/ファイル>: <指摘> — <提案/例>

テスト観点:
- <不足/改善案>

総評:
- <採用/条件付き承認/差し戻し> と理由
```

生成規則（AI向け指示）:

- 入力に沿って簡潔さを最優先。重複や抽象的な表現は避ける。
- 指摘は具体例と改善案をセットで提示。
- ハイリスク（セキュリティ/破壊的変更/大幅な複雑性増）は必ず先に列挙。

# AWS Bedrock/ベクトルサービス移行評価

## 現状のアーキテクチャ

- **書き起こし**: Whisper CLI（ローカル実行、GPU必要）
- **ベクトルDB**: Qdrant（Docker/Cloud）
- **Embedding**: OpenAI API（text-embedding-3-small）
- **デプロイ**: Render（Docker）またはAWS App Runner

## AWS移行の選択肢

### 1. 書き起こし（Transcription）

#### オプション A: Amazon Transcribe
- **コスト**: $0.024/分（約$1.44/時間）
- **メリット**:
  - 完全マネージド、スケーラブル
  - リアルタイムストリーミング対応
  - 話者分離、カスタム語彙対応
  - AWS統合が容易
- **デメリット**:
  - OpenAI Whisper API（$0.006/分）の4倍のコスト
  - 精度はWhisperの方が高い場合がある

#### オプション B: AWS Bedrock（Claude/Whisper等）
- **コスト**: モデル依存（概算 $0.01-0.03/分）
- **メリット**:
  - AWSエコシステム内で完結
  - 複数モデル選択可能
- **デメリット**:
  - 書き起こし専用サービスではない
  - コストが高い可能性

#### オプション C: 現状維持（Whisper CLI）
- **コスト**: インフラコストのみ（GPU必要）
- **メリット**:
  - 無料（オープンソース）
  - データが外部に出ない
  - カスタマイズ可能
- **デメリット**:
  - GPUインスタンスが必要（月$276+）
  - 運用・メンテナンス負荷
  - スケーラビリティに課題

#### 推奨: **現状維持（Whisper CLI）または OpenAI Whisper API**
- 小規模プロジェクトではローカルWhisper CLIが最もコスト効率が良い
- スケールが必要になったら OpenAI Whisper API（$0.006/分）が最も安価
- Amazon Transcribeは高コストで、このユースケースには過剰

---

### 2. ベクトルDB

#### オプション A: AWS Bedrock Knowledge Bases
- **コスト**: バックエンド依存（OpenSearch Serverless等）
- **メリット**:
  - 完全マネージドRAGソリューション
  - データ取り込み・チャンキング・埋め込み生成を自動化
  - AWS統合が容易
  - セキュリティ機能が充実
- **デメリット**:
  - 柔軟性が低い（ワークフローが固定）
  - 既存のQdrant実装を大幅に書き換えが必要
  - コストが高い可能性（OpenSearch Serverless等）
  - ベンダーロックイン

#### オプション B: Amazon OpenSearch Service（マネージドクラスタ）
- **コスト**: インスタンスサイズ依存（概算 $50-200/月）
- **メリット**:
  - フル機能の検索エンジン（全文検索 + ベクトル検索）
  - ハイブリッド検索（BM25 + ベクトル）が可能
  - Bedrock Knowledge Basesのバックエンドとしても使用可能
- **デメリット**:
  - 運用コストが高い
  - 小規模プロジェクトには過剰
  - Qdrantより複雑

#### オプション C: Amazon Aurora PostgreSQL with pgvector
- **コスト**: Auroraインスタンス依存（概算 $50-150/月）
- **メリット**:
  - PostgreSQLとベクトル検索を統合
  - 既存のRDBと同一データベースで管理可能
  - Bedrock Knowledge Basesのバックエンドとして使用可能
- **デメリット**:
  - ベクトル検索性能はQdrantより劣る可能性
  - スケーラビリティに課題
  - 運用コストが高い

#### オプション D: 現状維持（Qdrant）
- **コスト**: Qdrant Cloud無料枠またはDocker（$0-10/月）
- **メリット**:
  - 高性能なベクトル検索に特化
  - 低コスト（無料枠あり）
  - シンプルで軽量
  - 既存実装を維持できる
- **デメリット**:
  - AWSエコシステム外
  - マネージドサービスが限定的

#### 推奨: **現状維持（Qdrant）**
- 小規模プロジェクトではQdrantが最適
- コスト効率が高い（無料枠あり）
- 既存実装を維持できる
- 将来的にスケールが必要になったら、Bedrock Knowledge Basesへの移行を検討

### 3. Embedding

#### オプション A: AWS Bedrock Titan Embeddings
- **コスト**: $0.0001/1,000トークン（概算）
- **メリット**:
  - AWSエコシステム内で完結
  - マネージドサービス
- **デメリット**:
  - モデル選択が限定的
  - OpenAIより性能が劣る可能性
  - コスト比較が必要

#### オプション B: 現状維持（OpenAI Embeddings）
- **コスト**: text-embedding-3-small は $0.02/1Mトークン
- **メリット**:
  - 高精度
  - 低コスト
  - 既存実装を維持できる
- **デメリット**:
  - AWS外サービス

#### 推奨: **現状維持（OpenAI Embeddings）**
- コスト・性能のバランスが良い
- 既存実装を維持できる

## 総合評価と推奨

### 現状維持を推奨する理由

1. **コスト効率**
   - Qdrant: 無料枠または低コスト
   - OpenAI Embeddings: 低コストで高精度
   - Whisper CLI: ローカル実行で無料

2. **実装の簡潔性**
   - 既存の実装を維持できる
   - シンプルなアーキテクチャ
   - 学習コストが低い

3. **柔軟性**
   - ベンダーロックインを避けられる
   - カスタマイズが容易
   - 段階的な移行が可能

### AWS移行を検討すべきタイミング

以下の条件が揃った場合にAWS移行を検討：

1. **スケール要件**
   - 月間100時間以上の書き起こし
   - 大規模なベクトル検索（100万+ベクトル）
   - 高トラフィック（1000+ req/day）

2. **運用要件**
   - 24/7監視が必要
   - 自動スケーリングが必要
   - マルチリージョン展開が必要

3. **コスト**
   - AWS利用量が増えて割引が適用される
   - 企業アカウントでAWSクレジットがある

4. **統合要件**
   - 他のAWSサービス（S3、Lambda等）との統合が必要
   - AWSセキュリティ要件（コンプライアンス）が必要

### 段階的移行戦略（将来）

もしAWS移行を検討する場合の推奨順序：

1. **Phase 1**: ベクトルDBのみ移行
   - Qdrant → Amazon OpenSearch Service（マネージドクラスタ）
   - または Aurora PostgreSQL with pgvector
   - 既存のEmbedding（OpenAI）は維持

2. **Phase 2**: Embedding移行
   - OpenAI → AWS Bedrock Titan Embeddings
   - コスト・性能を比較検証

3. **Phase 3**: 書き起こし移行
   - Whisper CLI → Amazon Transcribe または OpenAI Whisper API
   - スケール要件に応じて判断

4. **Phase 4**: 完全マネージド化（オプション）
   - Bedrock Knowledge Basesに移行
   - ワークフロー全体をマネージド化

---

## 結論

**現時点ではAWS Bedrock/ベクトルサービスへの移行は推奨しません。**

理由：
- 小規模プロジェクトでは現状の構成がコスト効率が高い
- 既存実装を維持できる
- 将来的なスケール要件が明確になった時点で再評価可能

**ただし、以下の場合はAWS移行を検討：**
- 月間100時間以上の書き起こしが必要
- 大規模なベクトル検索が必要
- AWSエコシステムとの統合が必要
- 企業のコンプライアンス要件がある

- ✅ **YAGNI原則の理解**: 過剰な最適化を避け、必要十分な実装
- ✅ **実装の簡潔性**: シンプルで保守しやすいアーキテクチャ
- ✅ **ベンダーロックイン回避**: 柔軟性と将来の選択肢を保持

**採用担当者へのメッセージ：**
- 「小規模プロジェクトでは過剰なインフラは不要」という判断力
- 「コスト効率を重視した実用的な設計」というビジネス感覚

- ✅ **最新技術への対応**: 最新のマネージドサービスを活用
- ✅ **エンタープライズ対応**: スケーラブルで堅牢なアーキテクチャ
- ✅ **AWS認定への関連性**: Solutions Architect、ML Specialty等の学習に直結
- ✅ **実装の複雑さ**: より高度な技術スタックの運用経験

**採用担当者へのメッセージ：**
- 「AWSの最新サービスを実践的に使える」という技術力
- 「エンタープライズレベルの設計ができる」という経験
- 「学習意欲が高い」という姿勢

**デメリット：**
- 小規模プロジェクトには過剰に見える可能性

### 推奨：**ハイブリッドアプローチ（ポートフォリオ最適解）**

ポートフォリオとして最も効果的なのは、**両方の選択肢を提示し、適切な判断をしたことを示す**ことです。

#### 実装方針

1. **基本実装**: 現状維持（Qdrant + OpenAI + Whisper CLI）
   - 実用的でコスト効率の良い構成
   - 実際の運用に適している

2. **ドキュメント化**: AWS移行の評価と判断根拠を明記
   - このドキュメント（`aws_bedrock_evaluation.md`）をREADMEにリンク
   - 「なぜAWSを選ばなかったか」を明確に説明

3. **オプション実装**: AWS版の実装を別ブランチで用意（時間がある場合）
   - `feature/aws-bedrock` ブランチで実装
   - 比較できるように両方の実装を提示

#### ポートフォリオでの説明例

```markdown
## 技術選定の考え方

本プロジェクトでは、以下の理由から Qdrant + OpenAI + Whisper CLI を採用しました：

1. **コスト効率**: 小規模プロジェクトでは無料枠または低コストで運用可能
2. **実装の簡潔性**: シンプルで保守しやすいアーキテクチャ
3. **柔軟性**: ベンダーロックインを避け、将来の選択肢を保持

AWS Bedrock/ベクトルサービスへの移行も検討しましたが、
現時点では過剰な投資と判断しました。
詳細は [AWS移行評価](./docs/aws_bedrock_evaluation.md) を参照してください。

将来的にスケール要件が明確になった際は、
段階的なAWS移行を検討する予定です。
```

#### 面接での説明ポイント

1. **技術選定のプロセス**
   - 「AWSも検討したが、プロジェクト規模を考慮して現状の構成を選択」
   - 「コスト・複雑さ・将来性を総合的に判断」

2. **両方の技術を知っていること**
   - 「AWS Bedrock Knowledge Basesの仕組みも理解している」
   - 「適切なタイミングで移行できる準備はできている」

3. **実用的な判断力**
   - 「過剰な最適化を避け、必要十分な実装を選択」
   - 「ビジネス要件に応じた技術選定ができる」
